    Why even the best agent passes only about one test in four

    /why

    A user workflow is a sequence of actions that completes a user goal and ends in an observable result. For example: browse products, add an item to the cart, check out and see the order confirmation.

    The agent can use the website but never read its code

    /task

    Each task starts from a local website that an expert built to reproduce selected features of a widely used service. The agent reaches it only through a browser: it can navigate, click, type and take screenshots, but never read the HTML, scripts or server code. It has up to 16 hours to write a full-stack site that looks and behaves the same, and it can return to the reference as often as it likes while it codes and tests. A URL path, such as /cart, identifies a route; the page at that route can show different states, such as an empty or full cart. Hidden tests check those states and the actions that change them. The agent never sees those tests.

    What the agent can use

    • Screenshots and interface state of the reference
    • Navigation, clicks, typing, scrolling and form submissions
    • Images and other media files from the reference
    • Its own email inbox for sign-up and verification flows
    • The task instructions and the runtime contract
    • A shell, build tools and a local browser for its own site

    What the agent never sees

    • The reference’s HTML, JavaScript and CSS
    • API responses and arbitrary scripts run in the page
    • The server’s source code
    • The hidden tests, reference captures and scores

    Three ways the rebuilds go wrong

    /findings

    We traced Grok 4.6 runs from what the agent observed, to the code it wrote, to the tests it failed, and compared runs with and without a human exploration trace.

    1Underexploration

    Agents visit the pages but seldom follow a workflow to its end

    By their first code edit, agents had visited nearly every core page and started nearly every core workflow, but had followed only a few to their final step. They stop a multi-step interaction before it ends, so they never see what a checkout confirms or what a saved record looks like afterwards.

    A human exploration trace, a log of browser actions with no page content, raised the scores. The largest gains came on websites where the agent exploring alone had passed no hidden tests.

    2Failure to implement observed behavior

    What agents observe rarely reaches their code

    We checked the behaviors that an agent had observed during exploration and that its trajectory and submitted code let us verify: page contents, workflows and persisted state. Almost none were implemented the way the agent had seen them.

    Effort is lopsided too. Most tool calls explored the reference or checked the rebuild, and only a small share edited code.

    3Early stopping

    Agents stop with most of the clock left

    Runs may take 16 hours, yet most ended well before the limit. We then enabled Claude Code’s /goal hook for Kimi K3 on the Lowe’s task, so that a review had to accept each attempt to stop.

    At 10.25 hours the agent declared its repairs complete. The hook rejected the exit, and the agent went on to check that cart, order, account and session state survived a restart. The score rose from 0% to 31.3%.

    70 expert-built sites, 46,916 tests, no partial credit

    /tests

    Each site reproduces a widely used service

    Web developers designed and built the tasks under shared guidelines. For each website, one expert implements the reference and another reviews it for correctness and workflow coverage, then writes the hidden tests. Each site reproduces selected pages and workflows of a widely used service, with email and payments replaced by local services. A task has between 302 and 2,016 hidden tests.

    Three groups of hidden tests

    T1

    Request

    Direct HTTP checks of page responses and native form submissions.

    T2

    Browser

    Browser tests check interface responses and state changes. Workflow tests repeat a sequence of user actions and check the result. Checks cover three levels.

    1. L1An immediate response on one page, such as input validation.
    2. L2A state change read back in a later observation, on the same page or another, such as an edited record on its detail page.
    3. L3Persistence, other users and recovery, such as data after a restart.

    Some Browser tests add visual checkpoints that compare screenshots of marked regions with the reference.

    T3

    System

    Runtime requirements: offline builds, restarts, process health and security.

    All or nothing, test by test

    • A test earns its point only if its functional checks pass and every visual checkpoint reaches the similarity threshold.
    • Each browser workflow test repeats the same user actions with two independent executors, Playwright and Browser Use, and must pass with both.
    • Visual similarity is SSIM measured against a flat-color baseline, so large blank areas count for much less.
    • Every test weighs the same and there is no partial credit. A submission that copies the reference scores zero.
